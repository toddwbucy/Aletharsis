# Backend performance and resource characterization

This is workstream 6 of [Issue #7](https://github.com/toddwbucy/Aletharsis/issues/7). It measures the current text backend without changing detection, the report schema, acquisition guarantees, or the 8 MiB input cap. It does not introduce a scheduler or promise a service latency/memory limit.

## Reproduce

Use Linux, GNU `/usr/bin/time`, Go 1.27.1, and Python 3.12.13. Python runs this development-only harness; the audited executable has no Python dependency. Use a filesystem supporting the backend's required no-atime acquisition. Run from the repository root, on an otherwise idle machine with several GiB of available memory and disk space:

```bash
export GOTOOLCHAIN=local GOMAXPROCS=2
mkdir -p bin
go build -trimpath -o bin/aletharsis ./cmd/aletharsis
go test ./internal/benchmarks
python -m unittest discover -s benchmarks -p 'test_*.py' -v
python scripts/measure_backend.py --binary bin/aletharsis \
  --output /tmp/aletharsis-measurement --repeats 3 --timeout 120
ALETHARSIS_BENCH_SIZES=65536,1048576,8388608 \
  go test ./internal/benchmarks -run='^$' -bench=BenchmarkStages \
  -benchmem -benchtime=1x -count=3 -timeout=19m \
  > /tmp/aletharsis-stages.txt
```

The output directory must be new. Run process and stage measurements **sequentially**, not concurrently. Keep the executable unchanged between them. For a quick smoke test, pass `--sizes 65536 --repeats 1 --workers 1,2` and set `ALETHARSIS_BENCH_SIZES=65536` with `-count=1`. Neither smoke timings nor this first three-sample baseline establish statistical significance.

`.github/workflows/performance.yml` runs the quick profile when performance tooling changes and offers quick/full manual dispatch. It uses pinned compilers/actions, finite per-process and overall timeouts, and retains measurement artifacts for 14 days. Correctness/completion failures fail the job; timing changes are not gating thresholds. Manual full runs require a runner with enough memory for these large reports. Hosted/shared hardware results must not be compared directly with the local baseline as if hardware were identical.

## Corpus and identities

`benchmarks/corpus.json` defines six synthetic, deterministic cases:

| Case | Contents and purpose |
| --- | --- |
| ascii | Ordinary words/digits; many coordinates even with no findings |
| multilingual | Latin accents, Greek, Arabic, Devanagari, Chinese/Japanese |
| source | Source-like Python text, docstrings and supplementary emoji; text is never executed |
| zero_width | Long alternating ZWSP/ZWNJ binary-alphabet sequence |
| periodic | Repeated visible characters separated by WORD JOINER |
| combining | One long combining-mark run, ending with distinct marks that exercise canonical ordering |

Sizes are 65,536, 1,048,576 and 8,388,608 **bytes**. Each generator reserves prefix/suffix bytes, repeats whole UTF-8 units, and fills the remaining budget with ASCII spaces. Stage and executable generators share the specification; a Go test checks exact sizes/valid UTF-8 and pinned 64 KiB hashes generated by the Python harness. The executable harness checks those same pinned hashes and records every generated file's SHA-256 and scalar count. All cases use `.txt` filenames, including source-like content, so this characterizes text analysis rather than language-aware parsing.

The inputs include dense offset/context findings and a pathological long combining sequence; they are not a representative distribution of real user documents or a proof of worst-case bounds. They do not cover DOCX/PDF, malformed encodings, arbitrary filesystem latency, or every adversarial text pattern.

`results.json` records corpus identities, executable SHA-256, Go build metadata, source commit/worktree status, harness/spec hashes, Python/kernel/CPU identity, core count, per-child GOMAXPROCS, and measurement parameters. `corpus-manifest.json` is also retained separately. Harness regression tests exercise valid finding exit statuses, malformed reports, process timeouts, retained partial output, and refusal to overwrite an experiment directory. JSON inspection verifies completion, input identity/size, and exit status; full strict-schema validation remains the independent integration suite's responsibility.

## What each metric measures

- **Parse:** `TextParser.Parse` on already acquired bytes. It includes decoding, scalar-to-byte coordinates, and parser evidence; excludes file acquisition and identification.
- **Analyze:** all six current analyzers on a freshly parsed document. Parsing and its allocations are outside the timed interval. It excludes pipeline orchestration/sorting.
- **Serialize:** pretty, ASCII-safe JSON from an already audited report. Report construction is outside the timed interval. `report_bytes/op` records the serialized length.
- **Audit:** snapshot acquisition, hashing, identification, parsing, analysis and report construction; excludes JSON serialization and CLI output.
- **Executable:** a fresh CLI process, GNU time wrapper, and stdout report written to disk. High-resolution wall time includes launch/file setup/cleanup; GNU time also records coarse wall and user/system CPU seconds. There is no explicit warm-up exclusion; all three samples are retained. Inputs were just generated and filesystem caches are warm.
- **Go `B/op` / `allocs/op`:** allocation totals during the timed stage, not live heap or process peak memory. The stage process is reused; input/report preparation and GC state can affect latency. These isolated stage measurements are not an additive decomposition of CLI runtime.
- **Peak RSS:** GNU time's maximum resident set for the CLI child, in Linux KiB. It excludes the Python harness, parent JSON decoding, and other processes. Compare RSS with RSS, not with Go cumulative allocation totals.

Stage fixture paths differ from CLI paths, so serialized byte counts can differ slightly. The report format stores complete text and per-scalar offsets, including an end boundary; a small finding count does not imply a small report.

The concurrency experiment runs twelve 64 KiB jobs (two of each corpus) with 1, 2 and 4 independent processes, each limited to GOMAXPROCS=2. It records batch throughput and per-process peaks separately. Batch time includes parent JSON validation/scheduling. The sum of the largest N individual peaks is labeled an **upper envelope**, not measured simultaneous aggregate RSS. Small-input throughput cannot justify parallel 8 MiB audits.

Successful full reports are deleted after inspection unless `--keep-reports` is supplied; their sizes/counts remain in the measurements. Failed/partial reports remain locally for diagnosis. CI uploads measurements, timings and stderr, not the large inputs/reports. Per-child timeouts terminate the owned process group; SIGINT/SIGTERM also terminate registered groups. Abrupt SIGKILL/runner loss can prevent cleanup or artifact retention.

## Resource decisions and frontend spike

The checked-in [initial baseline](../../benchmarks/baselines/linux-amd64-go1.27.1/README.md) supplies observations and proposed starting budgets. They are review guidance, not enforced limits or a public API contract. Repeat on intended deployment hardware before selecting hard budgets.

Before choosing a frontend viewer/editor, the mandatory large-report/Unicode-coordinate spike must:

1. Import retained reports generated with `--keep-reports`, compute and retain the SHA-256 of the exact imported report bytes, and preserve the separate source digest. Measure browser import/parse time, peak memory, scrolling, evidence selection and search latency.
2. Exercise both the clean ASCII report's millions of coordinates and dense invisible/combining reports. Reconstruct these artifacts locally from the pinned corpus rather than committing hundreds of MiB of reports.
3. Prove source byte offsets, Unicode scalar offsets and UTF-16 display positions agree across supplementary emoji, combining clusters, ZWJ, bidi controls and escaped/collapsed invisibles. This performance corpus alone does not cover all those coordinate cases; include existing coordinate/fuzz regression fixtures too.
4. Benchmark worker parsing, virtualized visible rows, and indexed/lazy evidence access before committing to a component. Avoid a DOM node or a UI object for every source scalar/offset. These are candidate approaches to test, not changes to the frozen report contract.
5. Measure the combined browser/backend memory envelope. The backend RSS figures exclude frontend report copies, parent decoders and any service process. Preserve the Occurrence/location-adapter contract and exact evidence even if the visual view is abbreviated.

No PRD or frontend requirement is relaxed by these measurements. Any compact-coordinate schema, streaming service, output limit or algorithm optimization should be proposed separately and pass the existing coordinate, parity, schema and integrity gates.

## Opt-in schema 2.0 probe

The harness accepts `--schema-version 2.0`, records that choice and validates
completed reports against the independent wire/semantic oracle. It separately
records an exact, empty-output `execution.resource_limit` rejection as a valid
measurement with `valid_report=false`; timeouts, malformed/partial reports and
other failures remain invalid measurements. Rejections must never be counted as
successful audits. Schema 1.0 remains the default measurement path.

The [initial v2 probe](../../benchmarks/baselines/v2-097b35e-linux-amd64/README.md)
exposes restrictive evidence budgets and expensive late rejection. It is retained
as acceptance evidence requiring further work, not a passing release benchmark.

The [follow-up v2 probe](../../benchmarks/baselines/v2-96d2201-linux-amd64/README.md)
records the corrected ordering-key/anchor budgets and early rejection check.
All 64 KiB cases and four 1 MiB cases now complete without evidence truncation;
remaining rejections and memory measurements are explicit. Review acceptance is
still required, and the 16 MiB report cap does not promise all 8 MiB sources fit.
